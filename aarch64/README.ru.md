# llm.asm на AArch64 (Cortex-A76 / Cortex-A55)

[English](README.md) · **Русский** · [简体中文](README.zh-CN.md)

Перенос движка [llm.asm](https://github.com/alesha-pro/llm.asm) для Linux (Qwen3-0.6B Q8_0) на ассемблер AArch64, написанный заново с GNU `as` и `ld`: без C и libc, статический ELF на 17 КБ (`build/asm-llm-arm64`). Файл модели (`.asmbin` v2), шаблон чата, токенизатор и формат вывода — те же, что у сборки x86-64.

## Чем отличается от кода x86-64

- `sdot` (скалярное произведение ARMv8.2) перемножает знаковые байты напрямую, трюк со знаком из x86 не нужен.
- При загрузке веса переупаковываются: по 4 строки вперемешку группами по 4 байта, как в `q8_0_4x4` из llama.cpp. Тогда один `sdot` с индексом считает сразу 4 строки, а x загружается один раз на 4 строки. Переупакованная копия сохраняет смещения файла. `--norepack` включает простое ядро по строкам.
- Есть два варианта ядра: с программной предвыборкой для Cortex-A76 и без неё для Cortex-A55 — на ядре без внеочередного исполнения предвыборка отнимает около 35%. Каждый поток закрепляется за одним ядром из маски `taskset` и выбирает вариант по `MIDR_EL1`. Главный поток, который делает всю последовательную работу, всегда садится на большое ядро.
- Работа раздаётся динамически: потоки забирают куски по 16 строк атомарным `ldadd` (LSE), быстрые ядра берут больше. Результат не зависит от того, какой поток считал какую строку.
- Потоки ждут через `ldaxr` + `wfe`.
- Переупакованные веса по умолчанию лежат на прозрачных больших страницах по 2 МиБ (`madvise`); `--nohugepages` это отключает.
- Не перенесены: интерактивный чат, сэмплирование (только жадный выбор), загрузочная ОС и `FAST_Q8=0`.

## Корректность

- Логиты и текст побитово совпадают на 1×A76, 4×A76, 1×A55, 4×A55 и на всех 8 ядрах.
- Относительно сборок x86-64 косинусная близость логитов после промпта — 0,99971. Две сборки x86-64 отличаются друг от друга на том же уровне (0,99970). Первые 15 из 64 жадных токенов совпадают с выводом x86-64, дальше срабатывает почти ничья: на этом шаге четыре кандидата лежат в пределах 0,23 друг от друга.

## Результаты

Плата: FriendlyElec CM3588 Plus (RK3588: 4× Cortex-A76 на 2,3 ГГц + 4× Cortex-A55 на 1,8 ГГц, 32 ГБ LPDDR4X), Debian 12, ядро 6.1. ## Выводы

- **Большие ядра.** На 1–2 A76 llama.cpp быстрее на 12–16%, на 4 A76 быстрее порт — на 7–12%: здесь упор в пропускную способность памяти, и меньшие расходы на синхронизацию окупаются. 34 ток/с на 4 A76 — лучший результат на плате.
- **Малые ядра.** На A55 при фиксированной DDR llama.cpp быстрее в 1,3–1,6 раза.
- **Частота памяти.** С регулятором по умолчанию, пока работают только ядра A55, память остаётся на 534 МГц; как только работает хоть одно A76, она поднимается до 2400 МГц. Поэтому задачам только на A55 по умолчанию не хватает памяти: на одном A55 порт ускоряется на 49%, если зафиксировать DDR.
- **Смешанный режим.** Если добавить A55 к четырём A76, оба движка замедляются: пропускная способность памяти уже исчерпана. Используйте 4 больших ядра: если разрешены все ядра, `-t 4` сам выбирает A76.
- **Промпт** обрабатывается пачками: матрицы — ядром с регистровыми блоками, внимание — одним заданием на слой, шаги для каждого токена распределены по потокам. На 4×A76 порт на 10% быстрее llama.cpp на промпте из 227 токенов (226 против 206 ток/с); в остальных случаях llama.cpp быстрее в 1,03–1,29 раза (при обработке по одному токену было в 2,3–5 раз).

## Автоматический выбор потоков и Qwen3-1.7B

Без `-t` движок запускает по потоку на каждое большое ядро из маски `taskset`, а если в маске только A55 — по потоку на каждое разрешённое ядро. Поэтому обычный запуск на всей плате сам садится на четыре A76: 34,4 ток/с вместо 28,6 на всех 8 ядрах. Куски работы — по 16 строк, если участвует хоть одно большое ядро, и по 256 строк, если только A55: 12,8 вместо 10,3 ток/с на 4×A55. `--chunk-shift n` задаёт 2^n строк для опытов.

## Промпт пачками

Та же схема, что и в сборке x86-64, по умолчанию 16 токенов за проход. Ядро прохода — регистровый блок «4 строки × 2 токена» на переупакованных весах: регистры весов каждого блока служат обоим токенам, поэтому на каждый токен группа строк читается из L1 вдвое реже. Для каждого токена суммы SDOT в int32 точные, а шаги с плавающей точкой те же, что в ядре для одного токена, поэтому логиты побитово совпадают с обработкой по одному токену на любом наборе ядер.

Само ядро на данных в L1 (`aarch64/kbench.s`), такты на строку, токен и блок из 32 значений: A76 — 1,93 (было 2,35), A55 — 8,1 (было 11,0).

Внимание всего прохода — одно задание пула на слой: кусок работы — две query-головы одного токена, которые читают одну и ту же kv-голову. Оценки считаются сразу для 2 голов × 2 позиций в 16 аккумуляторах с той же раскладкой и тем же порядком свёртки, что у скалярного произведения для одного токена, поэтому каждая загрузка q и K служит двум произведениям. Каждый блок из 32 выходных значений обеих голов остаётся в регистрах на всех позициях, а не читается и пишется в память на каждой позиции. Куски одной пары голов идут подряд, поэтому её строки K и V от токена к токену остаются в L2 ядра (512 КБ); при порядке «сначала токены» то же ядро на одном A76 не давало ничего. Логиты по-прежнему совпадают побитово.

Между проходами по матрицам сложения с остатком, RMSNorm, квантование активаций и SwiGLU идут заданиями пула, по токену на кусок (SwiGLU — по четверти токена), а задание внимания само квантует свои выходы. QK-нормировка, RoPE и копирование в KV-кэш выполняются внутри прохода Q/K/V: кусок — одна голова для всех токенов, и ядро применяет эти шаги к строкам, которые только что посчитало. Каждый шаг выполняет код для одного токена, поэтому логиты по-прежнему совпадают побитово. SwiGLU внутри прохода gate/up и сложение с остатком внутри проекций, как пробовали на x86-64, на этих ядрах оказались медленнее (`results/prefill-fused.txt`).

Обработка промпта, Qwen3-0.6B, токенов в секунду (3 прогона, каждый начинался при температуре ниже 65 °C; llama.cpp та же, что выше, `llama-bench -p 34,227`; `results/prefill-tiles.txt`, `results/prefill-attention.txt`, `results/prefill-steps.txt`, `results/prefill-fused.txt`):

| Ядра | 34 токена: по одному | 34 токена: пачками | 34 токена: llama.cpp | 227 токенов: пачками | 227 токенов: llama.cpp |
|---|---:|---:|---:|---:|---:|
| 4×A76 | 45 | 187–201 | 213 | 214–226 | 206 |
| 1×A76 | 27 | 57–58 | 60 | 52–54 | 57 |
| 4×A55 | 13 | 40–41 | 53 | 41,6–42,4 | 52 |

Против предыдущей версии в чередующихся прогонах QK-нормировка, RoPE и копирование в KV-кэш внутри прохода Q/K/V добавляют 7% на 4×A76 на промпте из 34 токенов (182 → 195 ток/с) и 2% — на промпте из 227 (221 → 226); на одном A76 и на 4×A55 разница от −1 до +4%. До этого шаги в пуле добавили 9% на 4×A76 и 7% на 4×A55 на промпте из 227 токенов, а внимание пачкой — 8–11%. Первая версия пачек (одна группа из 4 строк и один токен за раз) давала 150 / 47 / 29,5 ток/с на промпте из 34 токенов и 157 / 43 / 27,8 — на промпте из 227.

Что осталось, промпт из 227 токенов: на 1×A76 внимание занимает 0,44 с из 4,3 с (до внимания пачкой было 0,83 с): около 0,13 с — оценки, 0,06 с — softmax, 0,25 с — взвешенная сумма V, и половину этого времени ядро ждёт строки V из L2. На 4×A76 — около 0,15 с из 1,0 с. До слияния Q/K/V шаги для каждого токена занимали 0,11 с из 1,07 с на 4×A76 (в одном потоке было 0,20 с) и 0,38 с из 5,4 с на 4×A55 (было 0,82 с); на четырёх A76 — почти столько же, сколько на одном, то есть время уходило на пересылку строк токенов между ядрами. Слияние убирает эту пересылку для QK-нормировки, RoPE и копирования в KV-кэш; слить так же gate/up и остаток здесь не окупилось.

## Сборка и запуск

```bash
aarch64/build.sh                     # на машине AArch64 с Linux (GNU as + ld)
taskset -c 4-7 build/asm-llm-arm64 -m models/qwen3-0.6b-q8_0.asmbin -p "..." -n 64 -t 4
aarch64/bench_cores.sh build/asm-llm-arm64 <model.asmbin> <llama-bench> <model.gguf> 3 out.csv
(cd aarch64 && as -o ../build/kbench.o kbench.s && ld -static -o ../build/kbench ../build/kbench.o ../build/aarch64/matmul.o)
taskset -c 4 python3 aarch64/kbench.py build/kbench 1   # такты ядра на A76; для A55 — cpu0 и 0
```

Файл модели — тот же `.asmbin` v2, что и для x86-64 (`scripts/export_weights.py --scale-dtype fp16`).
